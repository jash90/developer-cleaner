Odzyskaj gigabajty zajęte przez node_modules i buildy

Developer Cleaner w jednym skanie znajduje foldery node_modules, foldery buildów, takie jak target z Cargo, Pods czy .next, i zmergowane Git worktree, a osobno współdzielone cache narzędzi deweloperskich. Pokazuje, ile miejsca naprawdę wróci na dysk, a nie tylko ile zajmują pliki na papierze.

Pobierz najnowszą wersję Kod na GitHubie

Open source na licencji MIT · React + Rust (Tauri 2)

Dysk zapełnia się sam, po cichu

Każdy projekt JavaScript ma własne node_modules, każdy build zostawia po sobie folder z wynikami, każda gałąź otwarta przez git worktree to kolejna pełna kopia repozytorium, a menedżery pakietów trzymają swoje cache poza projektami. Po kilku miesiącach robią się z tego dziesiątki gigabajtów, których nikt nie pilnuje.

node_modules

Zostają w projektach, których nie otwierałeś od miesięcy. Gdy wrócisz do projektu, npm install je odtworzy.

Foldery buildów

target z Cargo, Pods, .next, .nx, .turbo, .cxx, coverage, .expo. Następny build albo instalacja je odtworzy.

Zmergowane worktree

Gałąź dawno trafiła do main, a jej katalog roboczy razem z zależnościami wciąż leży na dysku.

Cache narzędzi

npm, pnpm, bun, yarn, uv, Gradle, stare przeglądarki puppeteer i wersje Node z nvm. Żyją poza projektami.

Dlaczego „rozmiar folderu” często kłamie
Przypadek Co pokazuje naiwne liczenie Ile naprawdę odzyskasz
node_modules z pnpm lub bun pełny rozmiar każdego pliku prawie nic: pliki to hardlinki do wspólnego store'u, dane przetrwają usunięcie
Pliki rzadkie (obrazy dysków VM) rozmiar nominalny, czasem setki GB tylko bloki, które faktycznie zapisano
Pliki wyrzucone do chmury (iCloud Drive) rozmiar nominalny nic, bo tych bajtów nie ma na tym komputerze

Co potrafi

Najpierw przegląd, potem osobna strona dla każdej kategorii i jeden panel przeglądu, zanim cokolwiek zostanie usunięte.

Przegląd

Najpierw przegląd, potem szczegóły

Po skanie widzisz od razu, ile miejsca możesz odzyskać i skąd ono pochodzi, a nie długą listę folderów do przewijania.

  • Suma do odzyskania i pasek dysku: udział każdej kategorii, wolne miejsce teraz i po usunięciu wszystkiego, co znaleziono.
  • Cztery karty z sumą i największymi pozycjami każdej kategorii. Review all › otwiera pełną listę.
  • Sugestie od najbezpieczniejszych. Jednym kliknięciem zaznaczają tylko pozycje o niskim ryzyku z jednej kategorii, na przykład porzucone store'y albo czyste, niezablokowane worktree. Pozostałe otwierają przefiltrowaną listę do przejrzenia.
  • Karty wypełniają się, gdy wraca każdy skan. Postęp jest liczony względem poprzedniego skanu tego samego folderu, a Stop przerywa skan bez pokazywania niepełnych wyników.
node_modules

Szybki skan i uczciwe rozmiary

Wskaż folder, na przykład ~/Projects, a Rust przeskanuje go równolegle (Rayon).

  • Każdy wiersz pokazuje, ile miejsca faktycznie wróci. Gdy rozmiar nominalny jest inny, widać go po najechaniu na rozmiar, razem z wyjaśnieniem, skąd ta różnica.
  • Menedżer pakietów rozpoznany po lockfile: npm, yarn, pnpm albo bun.
  • Technologie z package.json jako etykiety: next, react, expo, @nestjs, vue, astro i inne.
  • Sortowanie po nazwie, rozmiarze albo menedżerze; zaznaczanie pojedynczo lub wszystkich naraz.
Foldery buildów

Foldery buildów, tylko tam, gdzie zostawiło je narzędzie

Ten sam skan znajduje w projektach wyniki buildów i cache narzędzi: target z Cargo, Pods z CocoaPods, .next, .nx, .turbo, androidowe .cxx, coverage i .expo.

  • Folder trafia na listę tylko wtedy, gdy narzędzie, które go utworzyło, zostawiło ślady obok i w środku: target wymaga Cargo.toml obok i CACHEDIR.TAG w środku, Pods pliku Podfile i Manifest.lock, a coverage prawdziwego raportu pokrycia.
  • Nigdy, gdy Git śledzi cokolwiek w środku, więc zacommitowane Pods i foldery o tylko podobnej nazwie zostają nietknięte. To samo sprawdzenie powtarza się tuż przed usunięciem.
  • Każde narzędzie ma własną grupę i własne pole wyboru, a w nagłówku grupy notę „What you lose”, czyli ile kosztuje usunięcie: target z Rusta to pełna rekompilacja i utrata trzymanych tam binarek release'owych.
  • Nic nie zaznacza folderów kilku narzędzi naraz: ani zaznaczenie wszystkich node_modules, ani sugestie, które dla folderów buildów otwierają tylko przefiltrowaną listę.
Git worktree

Zmergowane worktree, także po squash merge

Aplikacja najpierw odświeża refy z remote'a, a potem porównuje każde worktree ze wszystkimi gałęziami bazowymi repozytorium: origin/HEAD, main, master, development i develop.

  • Rozpoznaje squash merge, domyślny tryb scalania na GitHubie, i nie zostawia przy tym obiektów w repozytorium.
  • Worktree z niezacommitowanymi zmianami można zaznaczyć, ale usuniesz je dopiero po wyraźnej zgodzie na utratę tych zmian. Worktree zablokowanych przez Git nie da się zaznaczyć.
  • Wpisy, których katalog już zniknął, są czyszczone przez git worktree prune.
  • Filtry: czyste, z niezacommitowanymi zmianami, zablokowane i takie, po których została tylko rejestracja w Git.
  • Gałęzie zostają. Usuwany jest tylko katalog roboczy.
Cache deweloperskie

Cache poza projektami, bez wybierania folderu

Te cache leżą w stałych miejscach, więc aplikacja skanuje je od razu po uruchomieniu, zanim wybierzesz folder.

  • npm (_cacache, _npx), bun, yarn Berry i Classic, stare wersje Gradle, stare buildy puppeteer, stare wersje Node z nvm.
  • Porzucone store'y pnpm, które zostały po zmianie domyślnej lokalizacji, odróżnione od store'u, którego pnpm używa teraz.
  • Aktywny store pnpm i cache uv trafiają do ich własnego prune, więc to, co wciąż jest używane, zostaje.
  • Logi Homebrew są opróżniane w miejscu, bo usunięcie pliku otwartego przez usługę nie zwolniłoby miejsca.
  • Select safe zaznacza tylko pozycje bezpieczne. Te do przejrzenia wybierasz świadomie.
Bezpieczeństwo

Jeden przegląd przed usunięciem

Wszystko, co zaznaczysz na dowolnym ekranie, czyli node_modules, foldery buildów, worktree i cache, trafia do jednego panelu Review and Remove…. Pokazuje on każdą kategorię z liczbą pozycji i miejscem do zwolnienia, a każdą pozycję możesz tam jeszcze odznaczyć.

  • Dla folderów buildów panel powtarza, co tracisz przy każdym zaznaczonym narzędziu, a dla cache ich notatki.
  • Worktree z niezacommitowanymi zmianami panel wymienia z nazwy w ramce przypiętej nad przyciskami. Remove and discard changes pozostaje nieaktywny, dopóki nie zaznaczysz, że te zmiany przepadną na zawsze, a domyślnym przyciskiem jest Keep Everything.
  • Gdy zmieni się lista takich worktree, na przykład po odznaczeniu jednego z nich, zgodę trzeba dać od nowa.
  • Ta zgoda obejmuje tylko wymienione worktree. Jeśli worktree czyste w chwili skanu ma zmiany, gdy klikasz Remove, usunięcie zostanie odrzucone.
  • Usunięcie zostanie odrzucone, jeśli od skanu w worktree pojawił się nowy commit.
  • Śmieci systemowe (.DS_Store, cookies watchmana) są raportowane osobno, bo nie są pracą, choć blokują git worktree remove.
  • Worktree zablokowanego przez Git aplikacja nigdy nie usunie na siłę.
  • Błąd w jednej kategorii nie zatrzymuje pozostałych. Wynik podaje dla każdej, ile usunięto, ile się nie udało i ile miejsca zwolniono.
Pasek menu

Działa w tle z paska menu

Po zamknięciu okna aplikacja zostaje w pasku menu. Dla obserwowanych folderów pokazuje wolne miejsce na dysku, na którym dany folder faktycznie leży, i liczbę worktree gotowych do usunięcia.

  • Odświeża się co 15 minut, po kliknięciu Refresh now oraz po każdym skanie i sprzątaniu.
  • Gdy lista w oknie nie zgadza się już z licznikiem w pasku menu, okno o tym mówi i proponuje ponowny skan.
  • Odświeżanie w tle nie łączy się z siecią i nie przechodzi przez node_modules.
  • Na macOS możesz ukryć ikonę w Docku.
  • Ustawienia pokazują, ile trwało ostatnie odświeżenie i ile procesów Git uruchomiło.

Jak to działa

Od wybrania folderu do wolnego miejsca w czterech krokach.

  1. Wybierz folder

    Kliknij Choose Folder… i wskaż katalog z projektami.

  2. Poczekaj na skan

    Jeden skan znajduje foldery node_modules, foldery buildów i zmergowane worktree. Karty wypełniają się, gdy wraca każdy skan, a Stop go przerywa.

  3. Przejrzyj wyniki

    Przegląd pokazuje sumę, sugestie i największe pozycje każdej kategorii, a Review all › pełną listę. Zaznacz to, czego nie potrzebujesz.

  4. Usuń zaznaczone

    Kliknij Review and Remove…, przejrzyj zebrane zaznaczenie i potwierdź. Wszystkie kategorie, łącznie z cache, czyścisz za jednym razem.

Cache deweloperskie nie wymagają wybierania folderu: aplikacja skanuje je przy starcie, a Rescan caches skanuje je ponownie. Przejrzyj grupy i przy każdej pozycji sprawdź, jak zostanie wyczyszczona: usunięta, opróżniona w miejscu czy przekazana do prune narzędzia, do którego należy. Zaznaczone cache trafiają do tego samego przeglądu Review and Remove….

Pobierz albo zbuduj ze źródeł

Gotowe instalatory są w GitHub Releases. Możesz też zbudować aplikację samodzielnie.

Instalatory

  • Windows.msi · x64
  • macOS.dmg · Apple Silicon i Intel
  • Linux.deb, .AppImage · x64

Przejdź do najnowszego wydania

Aplikacja nie jest podpisana cyfrowo:

  • macOS: kliknij prawym przyciskiem → Otwórz, żeby ominąć Gatekeepera.
  • Windows: kliknij „Więcej informacji” → „Uruchom mimo to”.
  • Linux: ikona w zasobniku wymaga libayatana-appindicator3 (pakiet .deb ją deklaruje). Bez niej aplikacja działa, tylko bez zasobnika.

Budowanie ze źródeł

Wymagania: Node.js 18+, Rust (najnowszy stable) i narzędzia systemowe dla Tauri.

git clone https://github.com/jash90/developer-cleaner.git
cd developer-cleaner
npm install
npm run tauri dev     # tryb deweloperski
npm run tauri build   # instalatory w src-tauri/target/release/bundle/

Zależności systemowe:

  • Linux: sudo apt install libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf
  • macOS: xcode-select --install
  • Windows: Visual Studio C++ Build Tools
